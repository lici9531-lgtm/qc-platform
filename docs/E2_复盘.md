# E2 复盘（v1.1）

> 写作说明：「Jonh 原话」是 Jonh 自己写的；「启明补充」是学习教练根据这几天真实记录补的（帮助等级 H3）。

## 1. 做了什么

**Jonh 原话**：做了各个状态的检查逻辑，然后突然中断的恢复逻辑，有 run 和 dataset 两个接口。

**启明补充**：
- 服务做的事：登记一份标注 CSV → 创建质检工单 → 检查缺列、重复、坏行等问题 → 生成质检报告。
- 接口：`GET /health`、`POST /datasets`、`POST /runs`、`GET /runs`（按 status / dataset_id 筛选，limit/offset 分页，返回 `{items, total}`）、`GET /runs/{run_id}`、`GET /runs/{run_id}/report`。
- 工单状态：queued → running → succeeded / failed。
- 运行方式：Docker Compose 一次拉起 api + db；服务启动时把卡在 running 的工单标成 failed（interrupted）。
- 日志：每条带 run_id，正常 INFO，启动恢复 WARNING，失败 ERROR。

## 2. 关键取舍

**Jonh 原话**：runs 同步是因为当前的进程少而且快，方便操作和检查；分页上限 50 是为了避免一次加载太多，导致加载太慢；中断标成 failed 可以告知用户这个工单失败，如果自动重跑用户可能察觉不到，后面可以设置重跑次数和时间限制。

**启明补充**：
- 同步的代价：工单一多，接口会被卡住；以后改成 Redis 队列 + worker 异步执行。
- 上限 50 主要是保护数据库和接口：一次查太多行，查询和传输都会变慢（不是「存太多」）。
- 不自动重跑的另一个原因：可能有些步骤只做了一半，直接重跑会重复执行；而且如果工单本身有问题，重跑会一直失败，形成死循环。所以就算以后要重试，也要限制次数。

## 3. 踩过的坑（启明补充，均为真实记录）

| 现象 | 原因 | 怎么解决 |
|---|---|---|
| `docker compose kill api` 后 run 28 一直卡在 running，取报告返回 409 | 进程被杀，状态来不及改 | 加启动恢复：启动时把 running 的工单标成 failed |
| 容器里找不到 CSV | 容器有自己的文件系统 | Compose 加 bind mount `./data:/app/data:ro` |
| 工单跑得很慢 | `QC_DEMO_SLEEP` 演示用的延迟没改回 0 | 改回 `"0"` 并在容器内核实 |
| `~/qc-clone` 显示 clean，但停在 v1.0 | 它是本地克隆，origin 指向原目录，后来的提交它没有 | 用原目录推送，推送前先看 `git log` |

## 4. 已知不足（启明补充）

- `@app.on_event("startup")` 是旧写法，FastAPI 已经不推荐了，应该改用 lifespan。
- 时间没有统一用 UTC。
- pytest 会把测试数据写进真实数据库，应该给测试单独用一个库。
- `POST /runs` 是同步执行的，工单一多就会被卡住。

## 5. 下一步（启明补充）

1. 改用 lifespan，时间统一改成 UTC。
2. 给 pytest 单独配一个测试数据库。
3. 工单多了以后，用 Redis 队列 + worker 改成异步执行。
