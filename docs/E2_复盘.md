## 1. 目标

给 AI 训练团队做一个**标注数据质检服务**。数据量一大，人眼根本看不过来；写好程序来质检，准确率和效率都比人工高得多。它能判断数据是否正常、哪些行有什么错，并把错误归类。

## 2. 做了什么

用户先**登记 dataset**（提交 CSV 路径），再**创建 run**，服务才去读文件：
- 读不到文件或缺必需列 → run 为 `failed`，`error` 写清原因；
- 能读就逐行检查缺值、非法值、重复等，生成详细报告。

用户可以通过接口查进度、查报告。接口：`/health`、`POST /datasets`、`POST /runs`、`GET /runs`（筛选、分页、排序）、`GET /runs/{id}`、`GET /runs/{id}/report`。用 Docker Compose 一次拉起 api + MySQL。

## 3. 关键取舍

- **中断的工单直接判 failed，不自动重跑**：自动重跑用户察觉不到；有的工单本身就跑不成功，一直重跑会死循环。以后要重试就限制次数（比如 3 次），超过再判 failed。
- **`POST /runs` 先用同步**：现在工单少、跑得快，方便操作和检查；代价见「局限 1」。
- **分页上限 50**：避免一次加载太多导致变慢，保护数据库和接口。

## 4. 踩过的坑

工单跑到一半服务被杀，重启后状态还停在 `running`——进程死的时候来不及改状态。于是加了**重启恢复逻辑**：服务每次启动，把卡在 running 的工单标成 `failed`，error 写明 `interrupted`。（演练：2026-11-04 run 51）

## 5. 局限

1. `POST /runs` 是同步执行的，工单多或文件大时接口会被卡住。
2. `created_at` 存的是 UTC、又不带时区，读的人容易当成北京时间，差 8 小时。
3. `@app.on_event("startup")` 已被 FastAPI 弃用（pytest 有 3 条 warning）。
