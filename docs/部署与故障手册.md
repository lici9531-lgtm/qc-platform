# 部署与故障手册

> 运维向骨架。业务规则不在此展开。单 worker **同步**执行，**无 Celery / Redis / 自动重试队列**。

## 1. 部署步骤

### 1.1 首次部署

1. 安装 Docker / Compose；确认 `docker compose version`
2. `git clone` → `cd qc-platform`
3. `cp .env.example .env`，修改占位密码（勿提交 `.env`）
4. `docker compose up --build -d`
5. `docker compose ps`：`db` 为 healthy，`api` 为 running
6. 探活：`curl -s http://127.0.0.1:8000/`（**stub 阶段**返回占位 JSON；**待后端接入**后改为真实 `/health` 或业务探活）
7. （可选）初始化库表：挂载/执行 `db/init_db.sql`（**待后端接入**）

### 1.2 升级

1. `git pull`（或检出目标 tag，如 `v1.0`）
2. 核对 `.env.example` 是否有新增变量，合并进本地 `.env`
3. `docker compose up --build -d`
4. 观察日志：`docker compose logs -f --tail=200`
5. 跑通健康检查与一条 smoke（**待后端接入**：POST dataset / run）

| 对象 | 方法 | 期望 |
|------|------|------|
| Compose | `docker compose ps` | db healthy；api Up |
| MySQL | compose healthcheck（`mysqladmin ping`） | healthy |
| API stub | `curl http://127.0.0.1:8000/` | 200 + stub JSON |
| API 正式 | **待后端接入** | 约定探活路径 200 |

## 4. 常见故障

### 4.1 Compose 起不来

- 查：`docker compose config`、`docker compose logs`
- 常见：无 `.env`、语法错误、Docker daemon 未启
- 处理：补 `.env`；修 yml；重启 Docker

### 4.2 MySQL 未 ready / api 反复重启

- 现象：api 在 db 未 healthy 时连库失败（正式后端）
- 查：`docker compose ps`、`docker compose logs db`
- 处理：等 healthcheck 通过；检查密码/库名与 `DATABASE_URL` 一致；`start_period` 是否过短

### 4.3 端口占用

- 现象：`Bind for 0.0.0.0:8000/3306 failed`
- 处理：改 `.env` 中 `APP_PORT` / `MYSQL_PORT`，或释放占用进程

### 4.4 `.env` 缺失

- 现象：变量为空、容器退出
- 处理：`cp .env.example .env`

### 4.5 Volume / 权限

- 现象：MySQL 初始化失败、Permission denied
- 处理：勿手动乱改 volume 目录权限；必要时 `docker compose down` 后由官方镜像重建（**会丢未备份数据**时先备份）

### 4.6 API 5xx

- **待后端接入**后：查 `docker compose logs api`，按 `run_id` / request id 过滤
- 区分：应用异常 vs 连库失败 vs 规则执行失败（业务细节见产品文档，此处仅定位）

### 4.7 报告 409

- 章程口径：run 未到可出报告状态时可能 409（**待后端接入**）
- 处理：先 `GET /runs/{id}` 确认状态为 `succeeded` 再拉 report；勿当基础设施故障

## 5. 重启 / 中断恢复口径（与章程一致）

| 项 | 口径 |
|----|------|
| 执行模型 | 单 worker **同步**；无 Celery |
| 状态机 | `queued → running → succeeded \| failed` |
| 进程被 kill -9 / 容器强杀 | 启动扫描将卡在 `running`/`queued` 的僵尸 run 标 `failed`，`error=interrupted` |
| 自动重跑 | **不做** |
| 证据 | 应用日志中应有 interrupted 标记（**待后端接入**后验收）；运维侧保留 `docker compose logs` 截取 |

容器级重启（数据不丢）：

```bash
docker compose restart
# 或
docker compose down && docker compose up -d   # 不加 -v
```

## 6. 日志与 run_id 排查

```bash
docker compose logs -f api
docker compose logs --since 30m api
# 待后端接入后按 run_id 过滤，例如：
# docker compose logs api 2>&1 | grep '<run_id>'
```

排查顺序建议：Compose 状态 → db healthy → api 日志 →（有 run_id 时）库内状态（**待后端接入**）。

## 7. 回滚思路

- **镜像 / 代码**：检出上一 tag（如 `v1.0`）后 `docker compose up --build -d`
- **Volume**：`down -v` 会删数据；回滚应用一般**不要**删 `qc-platform-mysql-data`
- **备份提醒**：重要演练前 `docker run --rm -v qc-platform-mysql-data:/var/lib/mysql -v $(pwd)/backups:/backup alpine tar czf /backup/mysql_data_$(date +%Y%m%d).tar.gz -C /var/lib/mysql .`（示例；备份文件 `*.sql.gz` / 归档勿入库）
- 回滚后确认健康检查与一条 smoke

## 8. 明确不做（运维边界）

- 无前端、无 K8s、无微服务拆分
- 无 Celery / Redis / 自动重试队列
- 低置信度≠错标（产品口径一句带过，不在此展开）
